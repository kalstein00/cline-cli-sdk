# cline-cli-sdk를 사용하는 독립 챗봇 소비 앱

## Problem Statement

사용자는 `cline-cli-sdk`를 사용해 실제 챗봇을 만드는 방법과 실행 가능한 결과물을 보고 싶다. 다른 프로젝트에서도 SDK를 의존성으로 설치하고 같은 연동 방식을 사용할 수 있어야 한다.

현재 웹 예제는 연결·원격 작업·질문·진단 기능을 개별적으로 확인하는 테스트 화면이다. 요청과 메시지는 표시하지만, 대화 목록과 메시지 영역, 하단 입력창에서 대화를 이어가는 챗봇 소비 앱은 없다. 이 테스트 화면의 재생 기능만으로는 실제 SDK 사용법과 연속 대화를 보여줄 수 없다.

현재 SDK에는 `start`, `respond`, `attach`, `resume`가 있지만, 살아 있는 TUI가 응답을 마친 뒤 같은 실행에 다음 요청을 제출하는 공개 API가 없다. `respond`는 현재 질문에 대한 응답이고, `resume`는 종료 확인된 대화를 새 실행으로 이어가는 기능이다. 이 차이를 감춘 채 일반 챗봇의 후속 메시지 전송을 구현해서는 안 된다.

## Solution

`@cline-cli-sdk/sdk`를 정상적인 패키지 의존성으로 사용하는 **독립 챗봇 소비 앱**을 만든다. Node 서버가 SDK 공개 API를 호출하고 브라우저는 대화 목록·메시지·입력창·질문과 승인 UI를 제공한다. SDK가 챗봇 화면이나 제품 상태를 소유하지 않는다.

사용자는 연결 설정을 완료하고 새 대화에서 메시지를 보낸다. Cline의 답변과 필요한 질문·승인이 대화 안에 표시된다. 다음 메시지는 같은 대화에 이어지며, 연결을 끊었다가 돌아와도 원격 기록에서 대화를 복원한다. 기존 테스트 GUI는 진단·기능 확인용으로 유지하고 챗봇을 별도 실행 명령으로 제공한다.

다른 프로젝트의 개발자는 독립 예제의 서버 연동과 UI 계약을 참고하거나 가져다 쓸 수 있다. SDK 내부 소스, 이 저장소의 fixture, 테스트 서버, 원격 helper 구현을 직접 참조하지 않아도 동작해야 한다. 범용 배포 UI 라이브러리의 개발까지 이번 요구에 포함하지 않는다.

살아 있는 TUI의 후속 메시지 전송은 SDK의 별도 선행 기능으로 구현·검증한다. 챗봇은 그 공개 API를 소비하며 직접 키 입력이나 SSH 명령으로 부족한 기능을 우회하지 않는다. 이 선행 기능이 검증되기 전에는 챗봇의 연속 대화 구현을 완료로 처리하지 않는다.

## User Stories

1. 예제 앱 사용자로서, 한 명령으로 챗봇을 실행하고 브라우저를 열어 실제 소비 앱의 모습을 확인하고 싶다.
2. 예제 앱 사용자로서, SSH 별칭·원격 CLI·작업 디렉터리·격리 데이터 디렉터리를 설정해 내 시험 환경에 연결하고 싶다.
3. 예제 앱 사용자로서, 연결 전에 환경 점검 결과와 지원하지 않는 조건을 확인해 실행 가능 여부를 알고 싶다.
4. 예제 앱 사용자로서, 새 대화에서 첫 메시지를 보내 원격 작업을 시작하고 싶다.
5. 예제 앱 사용자로서, 사용자 메시지와 Cline 답변을 구분하는 대화 화면에서 진행 상황을 읽고 싶다.
6. 예제 앱 사용자로서, 답변이 갱신될 때 같은 메시지가 수정되도록 해 중복된 답변을 보지 않고 싶다.
7. 예제 앱 사용자로서, 답변 뒤 하단 입력창에서 후속 메시지를 보내 같은 대화를 이어가고 싶다.
8. 예제 앱 사용자로서, 한글·emoji·숫자로 시작하는 지원 범위 내 메시지를 원문 그대로 보내고 싶다.
9. 예제 앱 사용자로서, 입력 제한을 전송 전에 알고 초과한 초안을 수정하고 싶다.
10. 예제 앱 사용자로서, Cline의 선택 질문에 대화 화면에서 응답해 작업을 계속하고 싶다.
11. 예제 앱 사용자로서, 자유 응답이 가능한 질문에 입력창으로 답하고 현재 입력이 질문 응답임을 알고 싶다.
12. 예제 앱 사용자로서, 도구와 전체 승인 인자를 확인하고 명시적으로 승인하거나 거절하고 싶다.
13. 예제 앱 사용자로서, 전송 중·전달 확인·전달 여부 불명을 구분해 내가 보낸 내용의 상태를 알고 싶다.
14. 예제 앱 사용자로서, 중복 클릭이나 Enter 입력으로 같은 요청이 여러 번 실행되지 않게 하고 싶다.
15. 예제 앱 사용자로서, 지원하지 않는 상호작용을 확인하고 잘못된 대상에 응답하지 않고 싶다.
16. 예제 앱 사용자로서, 대화 목록에서 SDK가 관리하는 대화를 선택해 기존 기록을 읽고 싶다.
17. 예제 앱 사용자로서, 대화를 전환해도 이전 대화의 늦은 결과가 현재 화면을 덮어쓰지 않게 하고 싶다.
18. 예제 앱 사용자로서, 연결 해제와 원격 작업 중단을 구분해 필요한 행동을 선택하고 싶다.
19. 예제 앱 사용자로서, 브라우저나 로컬 서버를 다시 시작한 후 같은 원격 작업과 대화를 복원하고 싶다.
20. 예제 앱 사용자로서, 종료가 확인된 대화를 선택해 같은 대화의 새 실행으로 후속 요청을 보내고 싶다.
21. 예제 앱 사용자로서, 과거 메시지를 읽는 동안 새 출력 때문에 스크롤 위치를 잃지 않고 싶다.
22. 예제 앱 사용자로서, 한글 입력 조합 중 Enter가 메시지를 전송하지 않도록 하고 싶다.
23. 예제 앱 사용자로서, 원격 기록 읽기에 일시적인 문제가 생겨도 마지막 정상 대화를 유지하고 복구 상태를 알고 싶다.
24. 소비 앱 개발자로서, SDK 공개 API와 챗봇 서버의 연동 예제를 분리해 다른 프로젝트의 화면에 적용하고 싶다.
25. 소비 앱 개발자로서, 저장소 밖의 Node 프로젝트에서 packed SDK를 설치하고 챗봇을 실행해 배포 경계를 확인하고 싶다.
26. 소비 앱 개발자로서, 실제 CLI 검증과 기록 재생·장애 주입 결과를 구분해 예제의 지원 범위를 판단하고 싶다.

## Implementation Decisions

- **산출물 경계:** 독립 챗봇 예제 패키지, Node 서버의 SDK 연동 계층, 브라우저 대화 UI, 실행·다른 프로젝트 적용 안내를 만든다. 챗봇 제품 상태와 UI는 소비 앱에 둔다. SDK는 원격 연동 책임을 유지한다. DART 또는 특정 UI 프레임워크를 의존성으로 추가하지 않는다.
- **패키지 경계:** 예제는 패키지 이름과 공개 export만 import한다. 내부 모듈·테스트용 hook·상대 경로로 SDK 소스에 접근하지 않는다. 개발 편의를 위한 workspace 연결은 허용하지만 독립 설치 검증을 대신하지 않는다. 다른 프로젝트에는 packed SDK 설치 후 예제 자체의 시작 명령으로 실행하는 절차를 제공한다.
- **실행 경계:** 루트에서 `npm run example:chat`으로 챗봇을 시작하는 진입점을 추가하고 기존 `example:web`을 유지한다. 챗봇은 기본 `127.0.0.1:4174`에서 제공하며 포트를 설정할 수 있게 한다. Node.js 22 이상을 사용한다.
- **레이아웃:** 대화 목록, 현재 대화의 메시지 영역, 하단 입력창을 제공한다. 연결 설정은 접을 수 있는 영역에 둔다. 빈 화면에는 연결 또는 새 대화 시작 행동을 안내한다. 진단·프로토콜·원시 터미널 자료가 기본 대화 화면의 중심이 되지 않게 한다.
- **서버 연동:** Node 서버가 `createClient`, `connect`, `start`, `subscribe`, `snapshot`, `refresh`, `respond`, `listManagedExecutions`, `attach`, `resume`, `stop`, `disconnect`를 소비한다. 브라우저에는 챗봇에 필요한 상태와 제한된 행동만 전달한다. CLI 출력 파싱과 원격 helper 호출은 SDK만 수행한다.
- **최소 브라우저 계약:** 연결 점검, 관리 대화 목록 조회·선택, 새 대화의 첫 요청, 살아 있는 대화의 후속 요청, 질문 응답, 종료된 대화 재개, 상태 갱신, 연결 해제와 작업 중단을 제공한다. 현재 선택의 식별자·revision과 요청 ID를 전달하고 서버에서 현재 SDK 상태에 대조한다. 사용자가 임의의 원격 명령·키 바이트를 호출할 수 있는 endpoint는 제공하지 않는다.
- **대화 모델:** SDK가 발견한 실행을 session ID로 묶는다. 최초 session ID가 아직 없는 실행은 임시 실행 항목으로 표시하고 SID 확인 뒤 같은 항목으로 합친다. 대화의 여러 실행은 같은 대화에 속하지만 execution ID를 합치지 않는다. 목록 제목은 메모리에서 읽은 첫 사용자 메시지로 구성하고, 아직 기록을 읽지 않은 항목은 식별자 기반 제목을 사용한다.
- **선택과 동시성:** 한 번에 원격 작업 하나를 조작한다. 다른 대화로 전환할 때 새 SDK 클라이언트로 해당 실행에 attach한다. 이전 클라이언트의 구독·갱신을 정리하되 원격 작업을 중단하지 않는다. 선택 세대와 session/execution ID로 늦은 이벤트·HTTP 결과를 걸러낸다. 새 선택의 전체 snapshot이 확인되기 전에는 입력을 막는다. 응답 제출 중에는 선택 전환을 막고, 전달 여부 불명에서 벗어난 척하도록 클라이언트를 교체하지 않는다.
- **SDK 선행 기능:** 살아 있는 관리 TUI의 검증된 빈 Act composer에 후속 요청을 제출하는 공개 `sendMessage` 기능을 추가한다. 요청은 session ID, execution ID, 현재 revision, request ID와 원문을 포함한다. capability와 snapshot은 현재 후속 메시지 입력 가능 여부, 차단 이유와 전달 상태를 제공한다. 이 API는 질문 응답인 `respond`, 종료된 대화의 새 실행인 `resume`와 구분한다.
- **입력 가능성의 근거:** 단순히 질문이 없거나 spinner가 사라졌다는 이유로 후속 입력을 허용하지 않는다. 지원 CLI 프로필·TUI 모드·현재 history·살아 있는 동일 프로세스 identity·실제 focused 빈 composer·modal 부재·이전 요청 처리 상태와 해당 CLI의 작업 단계 근거를 SDK에서 함께 확인한다. 응답 생성 중이나 도구 실행 중에는 입력을 막는다. 답변 뒤 composer가 대기하는 상태를 실행 종료 또는 작업 성공으로 표시하지 않는다. 관찰로 안정적인 입력 가능성 판정이 성립하지 않으면 이 선행 작업을 미완료로 남긴다.
- **전송과 전달 확인:** 기존 SDK의 composer echo 검증, 분할 입력, 별도 Enter, 원격 단계별 ledger를 재사용한다. 입력 전 guard를 다시 확인한다. `sendMessage`는 현재 session/execution을 유지하고 새 CLI를 시작하지 않는다. 제출 전 history 경계 뒤에 원문과 일치하는 새 user 메시지를 확인해야 delivered가 된다. 같은 내용의 반복 메시지도 각각 다른 요청으로 정확히 한 번 전달할 수 있어야 하며, 과거의 같은 문구를 영수증으로 사용하지 않는다. delivered는 CLI 수신 확인이고 답변 완료가 아니다.
- **중복과 불명 상태:** 동일 request ID와 동일 요청은 기존 결과만 반환한다. 같은 ID의 다른 내용, 오래된 revision, 다른 실행, 동시 입력은 전송 전에 거부한다. 요청 제출 뒤 관측을 잃으면 전달 여부 불명으로 남기고 자동 재전송하지 않는다. 재연결 후 원래 ledger와 history 경계로 재대조하며, 여전히 불명인 상태는 새 request ID로 우회할 수 없다. 브라우저와 서버는 진행 중 요청 ID를 유지하고 HTTP 오류만으로 미전달로 단정하지 않는다.
- **첫 버전 입력 범위:** 새 후속 요청과 종료된 대화의 재개 요청은 우선 기존 composer 경로와 같은 printable 단일 행 UTF-8 112바이트 범위로 제한한다. 앞뒤 공백·제어문자·불완전 surrogate·선행 CLI 명령/mention 및 SDK가 지원하지 않는 grapheme을 원문 변경 없이 거부한다. 한글은 글자 수가 아니라 UTF-8 바이트 수로 계산한다. 질문 자유 응답은 해당 상호작용의 기존 SDK 계약을 따른다. 첫 요청은 `start`의 실제 계약을 적용한다. 입력 용도마다 현재 제한과 초과 이유를 화면에 표시한다. 살아 있는 실행의 112바이트 전송도 신규 실측 대상이며 기존 resume 수용으로 대체하지 않는다.
- **입력창의 동작:** 새 대화는 `start`, 검증된 살아 있는 대화의 후속 요청은 `sendMessage`, 자유 응답 질문은 `respond`를 사용한다. 선택·승인은 대화 안의 전용 버튼을 사용한다. 종료된 대화는 재개임을 안내한 뒤 `resume`를 사용한다. 실행 중·선택/승인 대기·미지원·기록 불명·전달 불명에서는 일반 후속 메시지를 보내지 않는다. 화면의 보내기 버튼도 현재 입력 용도를 표시한다. 자동 stop→resume를 일반 전송으로 숨기지 않는다.
- **전송 UI:** Enter와 보내기 버튼을 제공하되 IME 조합 중 Enter는 무시한다. 첫 버전에서 줄바꿈 입력은 명시적으로 거부한다. 쓰기 전에 거부된 입력은 초안을 유지한다. 제출된 입력은 pending 영역에 두고 원격 user 메시지 확인 뒤 message ID에 연결해 중복 표시하지 않는다. 요청 수신 여부가 불명인 경우 초안이 사라졌다는 이유로 재전송하지 않는다.
- **메시지 표시:** 공개 message ID 기준으로 추가·갱신하며 원문을 안전한 텍스트로 표시한다. SDK가 제공한 thinking은 접힌 영역에서만 표시하고 가려진 내용을 복원하지 않는다. history 재동기화가 실패하면 마지막 정상 메시지를 유지한다. 바닥 근처에서만 자동 스크롤하고, 과거를 읽는 사용자는 새 메시지 안내로 이동할 수 있게 한다.
- **복구와 저장:** 연결 설정·선택된 관리 실행 식별자 등 최소 메타데이터만 로컬에 보존한다. 대화·초안·원격 출력·키 내용·인증 파일을 기본 영구 저장 대상으로 삼지 않는다. SSH 키 파일 경로도 기존 예제의 저장 정책에 맞춰 보존하지 않는다. 로컬 서버 재시작 후 목록과 attach로 복원하며 입력 요청을 재실행하지 않는다.
- **지원과 보안 경계:** 검증된 공개 Cline 프로필의 terminal/TUI를 먼저 지원한다. JSON 출력은 양방향 챗봇 입력 경로로 사용하지 않는다. 회사 fork 호환성은 별도 검증 전까지 미검증이다. 로컬 서버는 loopback에 바인딩하고 기존 예제의 Origin·JSON 요청 제한을 유지한다. SDK 내부 인증 자료가 브라우저 응답·이벤트에 포함되지 않아야 한다. 진단은 기존 SDK opt-in API를 사용하며 자동 수집·외부 반출을 추가하지 않는다.

|---|---|---|
| 1 | 공개 CLI의 답변 후 살아 있는 composer·작업 단계 관찰, SDK 후속 메시지 계약 확정 | 입력 가능/차단 상태를 실제 자료로 구분한다. 기존 `respond`·`resume`와 책임이 구분된다. |

| 3 | 독립 챗봇 소비 앱의 Node 서버 연동 구현 | 공개 패키지 API만 사용해 연결·목록·시작·후속 입력·질문/승인·재개·중단·복구를 제공한다. |

| 5 | SDK 공개 API와 실제 브라우저·Windows→WSL 수용, 저장소 밖 설치 검증 | 아래 수용 기준을 충족하고 다른 프로젝트 적용 절차를 재현한다. |
| 6 | 실행·지원 범위·SDK 사용 흐름 문서 정리 | 새 챗봇 명령, 기존 테스트 GUI와의 용도, 독립 설치 절차, 입력 제한과 회사 미검증 범위를 명시한다. |

## Testing Decisions

사용자는 **SDK 공개 API를 주 테스트 접점으로 하고 실제 브라우저 검증을 추가하는 방향**을 확인했다. 새 내부 테스트 API를 만들지 않는다. SDK 입력 계약과 브라우저 소비 앱의 사용자 동작을 검증하고 내부 함수 배치·호출 횟수·CSS 구조는 고정하지 않는다.

- SDK 선행 기능은 기존 resume·text·delivery·reconnect·history-sync 공개 API 시험의 패턴을 재사용한다. 실제 CLI 원시 관측 fixture와 OpenSSH 경계 장애 주입을 구분한다.
- `sendMessage`의 정상 입력, 같은 문구 두 번, 같은 request ID 중복, 오래된 revision, 다른 실행, busy/질문/modal 상태, 입력 초과·한글·숫자 선행, echo 누락, Enter 뒤 연결 상실과 재대조를 검사한다. 차단만 하고 정상 연속 대화 지원을 완료로 세지 않는다.
- 새 SDK 행동의 원시 입력·관측·전달 근거를 진단 기록으로 수집하고 기존 공개 재생·비교 API로 복원한다. 정규화 snapshot을 재생 입력으로 사용하는 우회는 금지한다.
- 소비 앱은 브라우저에서 사용자가 수행하는 행동과 표시 결과로 검증한다. 서버 경계 장애 주입은 실측 성공을 대신하지 않고, 표시 상태·초안·중복 방지·선택 격리를 확인하는 용도로 사용한다.
- 실제 Windows 브라우저→Node→SSH→WSL의 고정 공개 CLI에서 첫 요청과 두 후속 메시지, 선택 질문·자유 응답·승인/거절, 단절·복원, 중단·재개를 수행한다. 예제 앱의 화면과 읽기 전용 원격 history/프로세스 증거를 대조한다.
- 저장소 밖 임시 Node 프로젝트에 packed SDK와 독립 예제만 설치한다. SDK 내부 소스·fixture·저장소 루트에 접근할 수 없는 상태에서 실행·정상 메시지 왕복을 확인한다. 이것이 다른 프로젝트에서의 사용 가능성에 대한 필수 증거다.

### 수용 기준

| ID | 확인할 외부 동작 |
|---|---|
| AC-01 | 별도 챗봇 명령으로 대화 목록·메시지 영역·하단 입력창을 가진 브라우저 소비 앱이 열린다. 기존 테스트 GUI도 별도 명령으로 실행된다. |
| AC-02 | 예제의 Node 서버가 설치된 SDK 공개 export만 사용한다. 브라우저와 예제 서버에 CLI 파서·직접 SSH·원격 helper 우회가 없다. |
| AC-03 | 첫 요청과 서로 다른 후속 요청 두 개가 같은 session ID로 이어진다. 살아 있는 composer 경로는 execution ID도 유지하며 전송 때문에 CLI를 재시작하지 않는다. |
| AC-04 | 한글·emoji·숫자 선행의 지원 범위 내 후속 입력이 원문 그대로 전달된다. 같은 문구를 별도 요청으로 두 번 보내도 각 경계 뒤에 정확히 하나의 user 메시지가 생긴다. |
| AC-05 | 입력 제한 초과·줄바꿈·지원하지 않는 입력은 원격 쓰기 전에 거부되고 초안이 유지된다. 112바이트 제한을 UI와 문서에 표시한다. |
| AC-06 | 생성/도구 실행 중·다른 modal·오래된 history·미지원 프로필에서는 일반 후속 입력이 차단되고 이유를 표시한다. 빈 composer만으로 준비 완료를 판정하지 않는다. |
| AC-07 | 선택·자유 응답·승인/거절이 현재 interaction ID/revision에 전달된다. 승인하지 않은 도구가 실행되지 않으며 질문 응답과 일반 후속 요청이 섞이지 않는다. |
| AC-08 | 더블클릭·반복 Enter·HTTP 중복은 같은 요청을 중복 제출하지 않는다. 한글 IME 조합 중 Enter는 전송을 발생시키지 않는다. |
| AC-09 | 제출 뒤 연결 상실은 전달 여부 불명으로 표시한다. 자동 재전송이나 새 요청 ID를 통한 우회가 없고, 복원 후 원래 요청의 수신 근거로 재판정한다. |
| AC-10 | 브라우저·로컬 서버 재시작 후 SDK 관리 대화를 조회·attach해 같은 원격 기록과 대기 질문을 복원한다. 복원 때문에 새 CLI나 user 메시지가 생기지 않는다. |
| AC-11 | 대화 전환 중 이전 이벤트·응답이 새 화면에 섞이지 않는다. 이전 질문의 응답이 새 실행에 전달되지 않는다. |
| AC-12 | 연결 해제는 원격 작업을 유지한다. 명시적 중단은 SDK confirmed 근거를 표시한다. 종료 확인된 대화의 재개는 같은 SID·새 EID를 유지하고 기존 메시지를 보존한다. |
| AC-13 | 메시지 갱신과 부분 history 실패에서 중복·빈 대화가 생기지 않는다. 과거 메시지를 읽는 사용자의 스크롤과 입력 초안이 보존된다. |
| AC-14 | 로컬 저장소에 대화·초안·원시 출력·인증 비밀을 기본 저장하지 않는다. 브라우저 응답·이벤트에도 인증 비밀이 노출되지 않는다. |
| AC-15 | packed SDK를 설치한 저장소 밖 독립 소비 앱에서 실제 첫 메시지와 후속 메시지 왕복이 된다. repo 내부 import나 시험 fixture 없이 실행된다. |
| AC-16 | 기존 SDK 회귀 시험과 새 공개 API 시험을 통과한다. 실제 브라우저·공개 CLI 실측·fixture/장애 주입·회사 미검증 결과를 분리해 보고한다. |

## Out of Scope

- 이번 스펙 발행 단계에서의 제품 코드 구현·배포·npm 공개 게시. 구현은 확정된 계획에 따른 후속 작업이다.
- 범용 챗봇 UI 패키지, React/Vue/Electron별 컴포넌트 배포, DART 실제 통합.
- SDK에 챗봇 제품 UI·대화 목록 화면·제품별 저장 모델을 넣는 것.
- 직접 모델 API를 호출해 Cline을 대체하는 챗봇, Cline 소스 수정, 공식 SDK/ACP를 통한 대체 연동.
- 여러 원격 작업의 동시 조작, 여러 소비 앱·사용자의 동시 제어, 공개 웹 서버·사용자 계정 서비스.
- 장문/여러 행의 일반 후속 요청, 첫 버전의 composer 입력 한도 확대. 이를 후속 지원으로 확장할 때 별도 실제 관측·수용이 필요하다.
- 파일 첨부·업로드, 음성, 검색/RAG, 스킬 관리, 대화 편집·삭제·분기·영구 로컬 아카이브.
- SDK가 관리하지 않은 임의 CLI 실행의 인계, 일반 터미널 화면이나 임의 키 입력 우회.
- 회사 실측 없이 회사 fork 호환성을 지원 완료로 선언하는 것.

## Further Notes

- 이 스펙은 기존 원격 연동 스펙 #1의 **독립 챗봇 소비 앱** 확장이다. 기존 웹 테스트 화면과 SDK 기능의 구현 사실을 챗봇 구현 완료로 간주하지 않는다.
- 사용자 보정: 핵심 목표는 SDK 자체에 챗봇을 넣는 것이 아니라, **cline-cli-sdk를 사용해 챗봇을 만들고 다른 프로젝트에서도 그 사용 방식을 적용할 수 있게 하는 것**이다.
- 2026-10-11 현재 SDK 소스·공개 export·예제·수용 문서를 확인했다. 살아 있는 실행의 일반 후속 입력 API는 아직 없고, 기존 `resume`는 종료 확인된 실행에만 적용된다.
- 112바이트는 짧은 대화를 시연하는 첫 버전의 제약이다. 일반 장문 챗봇을 완성했다고 표현하지 않는다. 이 제약을 UX에 숨기지 않으며, 독립 소비 앱 구조와 실제 연속 대화를 먼저 검증한다.
- 실제 CLI에서 안정적인 후속 입력 준비 상태를 확인할 수 없으면 SDK 선행 작업의 미충족 조건을 보고한다. 예제에서 자동 중단·재개 또는 직접 터미널 입력으로 대체하지 않는다.
- 회사 검증 #13은 별도 외부 입력 의존성이다. 이 예제의 공개 CLI 수용과 독립 설치 검증은 회사 호환성 검증을 대신하지 않는다.
- 기존 사용자 미커밋 자료는 보존한다. 스펙 발행은 해당 자료의 커밋·push·재배치를 포함하지 않는다.
